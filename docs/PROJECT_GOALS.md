# AI 角色扮演对话应用：重构与演进目标

> 文档状态：执行中
>
> 适用项目：`ai_roleplay_chat`
> 核心方向：先建立可验证、可演进的架构，再持续丰富角色扮演、故事创作、记忆、多媒体和助手能力。
> 最近更新：2026-08-04

## 1. 项目愿景

把当前应用从“功能集中、能够运行的 AI 聊天 Demo”演进为一个：

- Android 优先、本地优先、数据可控的 AI 角色与故事创作平台；
- 具备长期记忆、世界状态和人物关系演化能力的沉浸式对话工具；
- 能灵活接入多种 LLM、生图、TTS 和本地助手服务的开放客户端；
- 容易测试、维护、扩展和迁移的 Flutter 应用。

项目不追求单纯堆叠功能。新增能力必须建立在清晰的数据模型、稳定的业务边界和可靠的存储机制之上。

项目的核心竞争力是“角色表现真实”，包括：

- 角色对话中人格、认知、关系、状态和行为因果的真实；
- 故事模式中人物只能依据自身认知行动，不能因为叙事者掌握全局而表现出全知；
- 角色可以有依据地犹豫、协商、隐瞒或拒绝，但不能随机制造冲突；
- AI 可以表现角色的即时反应，但不得替用户主动推动故事主线。

## 2. 当前基线

当前版本已经具备：

- 角色、故事、opencode 助手三种联系人；
- OpenAI 兼容 LLM 接口；
- 短期、长期、超长期三级记忆；
- 关键词提取、事件图和 BFS 关联召回；
- 联系人 JSON 导入和自然语言创建；
- 图片生成、TTS、消息重发和单轮撤回；
- SharedPreferences 本地存储；
- 手机与桌面自适应界面；
- 248 项现有测试。

当前主要制约：

- `ChatProvider` 同时承担状态、业务、服务编排和持久化职责；
- `ChatPage` 同时承担页面布局、交互流程和大量消息组件；
- 联系人模型混合了实体、事件图算法和序列化；
- 设置存在多套读写入口，运行时状态不一定立即同步；
- 消息和联系人记忆没有统一事务边界；
- SharedPreferences 不适合持续增长的消息、事件图和媒体数据；
- 核心记忆级联、失败恢复和撤回行为缺少直接测试；
- 遗留字段、占位代码和文档存在漂移。

已确认的产品约束：

- 首要平台为 Android，其他平台兼容性暂不优先于 Android 体验；
- 联系人、消息、结构化事件和记忆应尽可能无损迁移；
- API Key 和旧应用设置不要求迁移；
- 保留三级记忆思想，不强行依赖向量数据库或完整知识图谱；
- 事件图和本地记忆允许较大容量，但必须有可配置上限，不能无限增长；
- 每轮只把检索得到的 RAG 结果输入 LLM，不把完整事件图塞入 Prompt；
- 模型生态先保留扩展接口，近期只完整维护具备测试条件的协议；
- 流式输出暂缓，不作为近期架构改造的前置条件；
- UI 允许重新设计；
- 新增依赖优先选择开源、维护活跃且 Android 可靠的项目。

## 3. 总体原则

### 3.1 行为优先

重构前先用测试锁定现有行为。任何目录调整或类拆分都不应暗中改变：

- Prompt 格式；
- LLM 输出解析；
- 三级记忆触发条件；
- 事件召回排序；
- 失败、重发和撤回行为；
- 旧数据读取结果。

### 3.2 本地优先

- 联系人、消息、记忆和设置默认只保存在用户设备；
- 外发给模型的数据必须可解释、可预览、可控制；
- API Key 等敏感信息使用平台安全存储；
- 导入、导出和备份格式需要版本号。

### 3.3 依赖方向单一

业务规则不能依赖 Flutter Widget、SharedPreferences 或具体 HTTP 客户端。

目标依赖方向：

```text
Presentation
    ↓
Application / Use Cases
    ↓
Domain
    ↑
Infrastructure implements Domain ports
```

### 3.4 小步迁移

- 不进行一次性推倒重写；
- 每个阶段都保持应用可运行、测试可通过；
- 先抽取纯逻辑，再替换存储和状态管理；
- 旧存储格式至少提供一个正式迁移周期。

### 3.5 可观测但不泄密

- 日志区分 debug、info、warning、error；
- 默认不打印 API Key、完整用户对话和完整 Prompt；
- 模型请求记录可由用户选择开启；
- 错误必须包含可操作的恢复建议。

### 3.6 事件先于文本

最低层记忆不是对可见文本的事后摘要，而是正文生成前先确定的“本轮事件”。

目标生成顺序：

```text
往期记忆级联概括
→ 本轮事件
→ 状态与知识变化
→ 角色回复或故事正文
```

因此：

- 本轮事件是本轮发生事实的规范化记录；
- 可见文本是本轮事件的具体演出和语言展开；
- 阶段记忆由多个本轮事件压缩而来；
- 长期脉络由多个阶段记忆进一步压缩而来；
- 不得在重构中把最低层记忆降格为对 `reply` 的事后概括。

### 3.7 真实不等于失控

- 角色可以拒绝，但拒绝必须有角色人格、目标、认知、关系或既往事件依据；
- 反应优先按“接受 → 犹豫/追问 → 协商 → 隐瞒/转移 → 拒绝 → 离开”渐进升级；
- 轻微后果可以自然发生，中等后果必须有明确原因，重大后果不得由 AI 无依据主动制造；
- 剧情内的后果可以长期有效，数据层必须可通过撤回、检查点或分支恢复；
- 故事模式允许局部即时反应，不允许擅自引入主线冲突、重要角色、重大秘密、时间跳跃或场景切换。

### 4.1 领域层

领域层包含稳定的业务概念：

- `Contact`：角色、故事或助手的身份和配置；
- `Conversation`：会话及消息顺序；
- `Message`：文本、图片、语音、系统事件等消息；
- `TurnEvent`：在可见文本之前生成的本轮规范化事件；
- `EpisodeMemory`：由多个本轮事件压缩出的阶段记忆；
- `LongTermThread`：由多个阶段记忆压缩出的长期脉络；
- `MemoryGraph`：事件节点和关系；
- `WorldState`：时间、地点、物品、人物状态和世界设定；
- `ProviderProfile`：模型能力声明，不包含 UI 状态。

领域服务建议包括：

- `MemoryCascadePolicy`：三级记忆何时压缩和迁移；
- `MemoryRecallService`：关键词、图关系和时间权重召回；
- `MemoryPatchReducer`：把 LLM 补丁转成新的领域状态；
- `PromptContextSelector`：在预算内选择上下文；
- `ConversationTransaction`：定义一轮对话的提交和回滚规则。
- `CharacterBehaviorPolicy`：约束角色自主性、认知边界和反应强度；
- `StoryControlPolicy`：区分角色即时反应与用户控制的剧情推进。

这些逻辑应尽量是无 Flutter 依赖的纯 Dart 代码。

### 4.2 应用层

每个用例只编排一个完整用户动作：

- `InitializeApplication`
- `CreateContact`
- `ImportContact`
- `SendMessage`
- `ResendMessage`
- `RecallLastTurn`
- `ReviseMemory`
- `CreateCheckpoint`
- `CreateConversationBranch`
- `GenerateImageFromMessage`
- `SpeakMessage`
- `ExportBackup`
- `RestoreBackup`

以 `SendMessage` 为例：

```text
校验输入
→ 创建本地 pending 消息
→ 提取召回线索
→ 选择记忆上下文
→ 构建 Prompt
→ 调用模型
→ 解析往期概括、本轮事件和状态补丁
→ 读取最后生成的可见文本
→ 计算新的记忆状态
→ 原子提交消息和记忆
→ 发布 UI 状态
```

### 4.3 基础设施层

基础设施负责替换性实现：

- LLM、图片、TTS、opencode HTTP 客户端；
- SQLite/Drift 或 Isar 数据库；
- SharedPreferences 轻量设置存储；
- Secure Storage 密钥存储；
- 文件导入、导出和媒体缓存；
- 日志与诊断报告。

上层只依赖接口，不直接依赖某个插件。

### 4.4 展示层

展示层只处理：

- 页面与组件渲染；
- 用户事件转发；
- loading、error、empty 等界面状态；
- 导航和一次性提示。

优先拆分：

- `ChatShell`
- `ConversationView`
- `MessageList`
- `MessageBubble`
- `MessageComposer`
- `ContactPanel`
- `ChatActions`
- `ImageGenerationDialog`
- `ProviderSettingsForm`

状态对象不应直接读写 SharedPreferences 或发 HTTP。

## 5. 架构改进目标

### 5.1 初始化统一

- 提供唯一的 `bootstrap()`；
- 所有设置、数据库、服务在 `runApp` 前或明确的启动状态中完成初始化；
- 禁止在构造函数中启动不可等待的异步加载；
- 初始化失败应能重试，并展示具体失败模块。

### 5.2 状态管理收敛

- 将页面状态、会话状态和全局配置状态分开；
- Provider/ViewModel 只公开不可变状态；
- 使用明确的状态类型，例如 `initial/loading/ready/failure`；
- 避免通过多个全局单例传播配置。

是否引入 Riverpod、Bloc 等框架可在完成业务拆分后决定，不把“换状态管理框架”本身当成重构目标。

### 5.3 存储升级

建议：

- SharedPreferences：主题、开关、轻量参数；
- Secure Storage：API Key、密码；
- SQLite/Drift 或 Isar：联系人、会话、消息、事件和边；
- 文件目录：图片、音频、导出包。

数据库需要：

- schema version；
- 自动迁移；
- 事务；
- 索引；
- 分页读取；
- 数据完整性检查；
- 从现有 SharedPreferences 导入的迁移器。

### 5.4 消息事务

一轮角色对话至少包含：

- 用户消息；
- AI 消息；
- 联系人状态；
- 事件图；
- 关键词库；
- 撤回快照或操作日志。

成功时统一提交，失败时保留明确的 failed 消息，但不得留下半更新记忆。

### 5.5 记忆引擎独立

把当前记忆逻辑从 `ChatProvider` 抽成独立模块，并为以下规则建立测试：

- 短期 → 长期；
- 长期 → 超长期；
- 自主总结；
- 队列容量和截断；
- LRU 权重；
- 事件边去重；
- BFS 深度；
- 物品和设定关联；
- 召回结果去重；
- Prompt 预算限制。

事件关系跨轮保留，但不是无限积累。默认目标是：

- 允许使用设备容量范围内的较大本地存储上限；
- 通过容量、重要度、时间、级联概括和用户锁定状态清理；
- 完整事件图只保存在本地；
- 每轮只把混合检索得到的少量 RAG 结果送入 LLM；
- 清理前保证上层阶段记忆或长期脉络已经覆盖被淘汰内容。

### 5.6 Prompt 与输出协议版本化

- 将 Prompt 模板从 Provider 中移出；
- 为角色、故事、摘要、关键词、生图润色分别定义模板；
- 每个模板包含版本号；
- 结构化输出使用明确 schema；
- 解析失败提供修复请求或降级策略；
- 建立 Prompt 快照测试。

结构化输出必须体现真实的生成顺序：

```json
{
  cascadeSummary: {
    description: 达到阈值时，对往期记忆进行级联压缩
  },
  turnEvent: {
    description: 本轮确定发生的核心事件,
    keywords: [],
    theme: [],
    relatedEventIds: []
  },
  memoryPatch: {
    worldKnowledge: [],
    selfKnowledge: [],
    userKnowledge: [],
    belongings: [],
    currentStates: {}
  },
  reply: 根据前述事件与状态展开的角色回复或故事正文
}
```

迁移期间可以继续读取旧 `summary`、`eventBrief` 字段，但新协议必须保证事件和状态出现在 `reply` 之前。

### 5.7 错误模型统一

统一错误类别：

- 配置错误；
- 网络错误；
- 鉴权错误；
- 限流；
- 超时；
- 响应格式错误；
- 存储错误；
- 数据迁移错误；
- 用户取消。

UI 根据类别展示重试、打开设置、复制诊断等操作。

### 5.8 角色行为真实性

角色行为由以下输入共同决定：

```text
角色身份与人格
+ 当前场景
+ 角色认知边界
+ 当前目标与动机
+ 关系状态
+ 本轮召回记忆
+ 世界规则
→ 本轮事件
→ 可见表现
```

角色不能：

- 知道自己没有经历、听说或合理推断出的信息；
- 为迎合用户无原因改变人格、底线或长期目标；
- 为制造戏剧性随机敌对、拒绝或离开；
- 把模型掌握的系统信息当作角色自身认知。

每个角色后续可配置三个独立维度：

- 人格坚持度；
- 合作倾向；
- 边界强度。

默认策略为“人格稳定、正常合作、边界明确”。

### 5.9 后果、检查点与分支

- 轻微状态变化可随互动自然发生；
- 中等后果必须能追溯到明确行为或事件；
- 重大后果只能来自用户明确推动或既定情境的必然后果；
- 不使用频繁确认弹窗破坏沉浸感；
- 每轮保存可逆操作记录；
- 每个场景建立检查点；
- 重大变化标记为关键节点；
- 用户可以撤回或从关键节点创建剧情分支。

### 5.10 历史档案与记忆修订

数据层次定义为：

```text
本轮事件：发生了什么
完整文本：事件如何被具体表现
世界状态：事件发生后的当前投影
阶段/长期记忆：更长时间尺度上的重要内容
```

完整历史默认不参与每轮 RAG，但用于：

- 用户回看、搜索和导出；
- 对话撤回、检查点和分支；
- 重新生成或修复上层记忆；
- 审计本轮事件是否在正文中得到一致表现；
- 数据迁移和一致性检查；
- 用户明确要求回查久远历史时的受控二次检索。

修改记忆采用“修订”而不是原地覆盖：

- 每条事件使用稳定 ID；
- 保存原始版本和当前有效版本；
- 修订后重新计算关键词和本节点索引；
- 相关边可以失效，但保留历史以支持撤销；
- 引用该事件的阶段或长期概括标记为待更新；
- 新修订在 RAG 中优先于旧摘要；
- 保存前向用户展示影响范围；
- 第一版至少支持修订、作废、影响标记和撤销修订。

## 6. 产品能力丰富路线

### 6.1 角色与世界构建

- 角色模板市场或本地模板库；
- 角色版本与复制；
- 世界书、地点、组织、规则和时间线；
- 多角色关系图；
- 角色状态面板；
- 人物好感、信任、阵营等可配置数值；
- 角色卡导入导出；
- 支持常见角色卡格式的兼容导入；
- 角色头像、背景图和主题色；
- 角色开场白与多套场景预设。

### 6.2 对话体验

- 编辑、删除、复制和引用消息；
- 从任意消息重新生成；
- 多候选回复与左右切换；
- 对话分支和树状时间线；
- 会话搜索；
- Markdown、代码块和富文本；
- 消息流式输出；
- 中止生成；
- Token 和费用估算；
- 上下文预览；
- 快捷指令和输入模板；
- 草稿自动保存；
- 键盘快捷键；
- 分页加载历史消息。

### 6.3 记忆系统

- 用户可查看、编辑、锁定和删除记忆；
- 标记错误记忆；
- 记忆来源追踪到具体消息；
- 记忆重要度、置信度和有效期；
- 自动合并重复或冲突记忆；
- 世界状态变更日志；
- 人物关系记忆；
- 时间线视图；
- 记忆召回调试器；
- 可选 embedding/向量召回；

### 6.4 故事创作

- 章节和场景管理；

- 叙事视角、文风和篇幅控制；
- 角色一致性检查；
- 世界设定冲突检测；
- 自动章节摘要；
- 分支剧情；
- 章节导出为 Markdown、TXT、EPUB；
