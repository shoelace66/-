## 1. 固定更新循环

每个更新批次严格按以下顺序推进：

1. **确认边界**：从本路线中选择一个能够独立交付的纵向切片，不同时铺开多个未闭环功能。
2. **锁定行为**：先补领域测试、存储测试或 Widget 测试，记录兼容行为与失败行为。
3. **领域建模**：业务规则进入纯 Dart 实体、策略、服务或用例，不新增 Widget/存储反向依赖。
4. **基础设施实现**：实现数据库 schema、迁移、repository、HTTP 客户端或文件服务。
5. **展示层接入**：UI 只调用用例或状态对象，补齐 loading、empty、failure、retry。
6. **迁移与恢复**：涉及数据格式时必须提供 schema version、幂等迁移、失败回滚和旧数据样本测试。
7. **完整验收**：依次运行格式化、`flutter analyze`、离线 `flutter test`、Android release APK 构建。
8. **更新记录**：更新本文件状态、`PROJECT_GOALS.md` 实施记录、README 能力与限制。

出现以下情况时暂停实现并向产品负责人确认：

- 会改变“用户控制剧情主线”或角色自主性边界；
- 会改变本地数据保留、外发内容或隐私默认值；
- 需要在互斥的数据模型或交互模型之间做长期选择；
- 会删除旧数据、旧导入格式或已公开能力；
- 需要新增闭源、收费或 Android 可靠性不足的关键依赖。

普通命名、文件拆分、内部算法和可逆 UI 细节由实现者直接决定。

## 2. 质量门禁

每个批次完成时必须同时满足：

- 领域规则的关键分支有纯 Dart 单元测试；
- 网络测试完全使用 fake/mock，不依赖公网；
- 数据写入具备事务边界，失败不会留下半提交状态；
- 新 schema 有迁移和回滚测试；
- `flutter analyze` 为 0 error、0 warning、0 info；
- 完整离线测试全部通过；
- Android release APK 构建成功；
- 日志不输出 API Key、完整 Prompt 或完整对话；
- README 和目标实施记录与代码一致。
